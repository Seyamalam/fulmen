# Fulmen 0.2.0 — M2 benchmark results

Milestone M2 exit-criteria measurements (docs/ROADMAP.md §M2, docs/DESIGN.md
§25). All numbers from this machine, release build (`just develop -r`), one
10 s `oha` pass per app per scenario unless noted. New for M2.17: `validated`
and `reject` POST scenarios plus a `fulmen_pydantic` app (pydantic `BaseModel`
bodies through the adapter → native `record` specs).

## Commands

```sh
just develop -r                                    # release extension into both venvs
uv pip install -p benches/e2e/.venv "pydantic>=2.7" -e .
cargo build -r -p fulmen-bench --bin ceiling-server
python benches/e2e/run.py --workers 12 --duration 10 --connections 100 --warmup 3 --set-baseline
python benches/e2e/run.py --apps fulmen,fulmen_async,fulmen_pydantic --scenarios validated,reject --workers 1
python benches/e2e/run.py --apps fastapi --scenarios validated,reject --workers 1
python benches/e2e/decode_smoke.py --seconds 60    # interim for the 1h fuzz soak
python benches/e2e/check.py                        # the `just bench-check` gate
```

Every Python app: 12 worker processes (`--workers 12`; Robyn's equivalent is
`--processes 12`). Ceiling is one process with 18 tokio threads — the
measured bound, not a competitor. No access logs anywhere. Each scenario:
3 s `oha` warmup, then a 10 s measured run at `-c 100 -w
--output-format json`. `validated`/`reject` POST a fixed ~240 B order record
(10 fields: str/int/float/bool, `list[str]`, nested `Geo`) to `POST
/validate` — valid satisfies every constraint, invalid violates six of them.

## Exit criteria

### (a) validated 10-field body ≥5× FastAPI

**Verdict: FAIL at the mandated 12-worker count; PASS per worker process —
same shape as M1(a).**

At the fairness-mandated 12 workers:

| app | `validated` req/s | vs fastapi 34,802 |
|---|---:|---:|
| fulmen sync | 65,797 | 1.89× |
| fulmen async | 106,462 | 3.06× |
| fulmen pydantic | 55,352 | 1.59× |

At `workers=1`, where per-process throughput is what the framework controls
(fastapi 1w measured at 2,915 req/s):

| app | `validated` req/s | vs fastapi |
|---|---:|---:|
| fastapi 1 worker | 2,915 | 1.0× |
| fulmen sync 1 process | 61,431 | **21.1×** |
| fulmen async 1 process | 102,944 | **35.3×** |
| fulmen pydantic 1 process | 41,422 | **14.2×** |

Why 12v12 compresses: fastapi parallelizes its pydantic work across 12
spawned uvicorn processes (~2.9k → 34.8k), while fulmen's per-process
validated number is already near its bound — sync is limited by the pool's
GIL handoff (~62k), async rides the loop thread (~103k) — so adding
processes adds scheduler spread, not throughput. The validation itself is
not the limiter: fulmen sync `validated` runs at 80% of its own `json`
number, and `reject` reaches 96% of the pure-Rust transport bound.

### (b) 422 path ≥20× FastAPI (invalid input never enters Python)

**Verdict: FAIL on the multiplier; the architectural property is exactly
as designed.**

| deployment | fulmen sync | fulmen async | fulmen pydantic | fastapi |
|---|---:|---:|---:|---:|
| 12 workers | 132,638 (1.67×) | 134,949 (1.70×) | 135,772 (1.71×) | 79,431 |
| 1 worker | 132,000 (12.5×) | 129,120 (12.2×) | 132,978 (12.6×) | 10,554 |

The property the criterion encodes holds and is counter-verified: **zero
Python handler calls during the reject window on every fulmen app** — the
descriptor answers 422 in Rust before dispatch. Throughput lands at 95–98%
of the pure-Rust ceiling (137,952): there is no more Python to remove.

The 20× factor does not hold on this stack because FastAPI's *reject* path
is its fastest measured route: a pydantic `ValidationError` short-circuits
inside starlette's async layer — it never enters the threadpool, so 12
workers reject at 79k, 2.3× faster than FastAPI's own `validated` column
(and faster than its `plaintext`). The criterion was plausibly calibrated
against a reject path priced like FastAPI's validated one (~3k/process);
measured single-worker it is 10.5k — an async-resident error path, not a
validation tax.

### (c) served OpenAPI document valid

**Verdict: PASS.** `check_openapi` runs inside `bench_app` for every
fulmen-flagged app and passed 10/10 on all three (sync, async, pydantic):
document parses, `openapi == 3.1.0`, `info.title` set, all five route paths
present, `/validate` requestBody is a `$ref` into
`components/schemas.Order`, `Geo` is a nested object component, required
fields (`order_id`/`customer`/`email`) and emitted constraints
(`minimum: 1`, `minLength: 1`, sku `pattern`) present, `geo` in properties,
a `200` response declared. `python/tests/test_openapi.py::
test_served_document_structure` walks the served document deeper — every
`in` legal, path params `required`, every local `$ref` resolves, component
schemas well-formed — and the same checks pass for pydantic-model bodies
(`test_pydantic.py::test_route_openapi_*`).

### (d) fuzzers 1 h each, no findings

**Verdict: PENDING — fuzz targets not merged.** `cargo-fuzz` 0.13.2 is
installed but M2.19's targets and the `just fuzz` recipe do not exist yet.
Interim guardrail (`benches/e2e/decode_smoke.py`, 60 s, 8 threads, hostile
corpus — deep nesting, 4 MiB strings, 200k-item arrays, boundary ints,
unicode/NULs, truncated/malformed JSON): **363,254 requests, zero 5xx,
zero hangs** — 12,537 valid 200s, 175,893 malformed-JSON 400s, 174,824
constraint 422s, 25,294 tolerated transport aborts (the server closes
oversized writes mid-body — expected rejection, not a crash). Post-soak
liveness 200. The 1 h `cargo fuzz` soak remains to run when M2.19 lands.

## Notes and honest caveats

- **flask contamination**: gunicorn's connection-close behavior exhausted
  loopback ports; the first pass's fulmen `plaintext` (67,179, 5,014
  `os error 49` events) ran inside the hangover window. Baseline self rows
  use an immediate clean re-run; flask ordering stays as-is (its numbers
  are context, not gated).
- **plaintext/item variance**: fulmen sync `plaintext` measured 67,179 →
  73,599 → 84,682 across three same-binary runs within minutes — ±15%
  ambient noise on the sync-pool path (p99 tail 8–13 ms; M1's 85,808 sits
  inside the band). `item` is stable at ~78–79k vs M1's 82,657 (−4–5%),
  inside the same envelope — no code path shared with the adapter changed.
- **Adapter tax**: `fulmen_pydantic validated` = 55,352 vs `fulmen` sync
  65,797 (−16%); at 1 worker 41,422 vs 61,431. The per-request
  `meta.after` finalize that restores `__pydantic_fields_set__`/
  `__pydantic_extra__`/`__pydantic_private__` is a Python callback on the
  hot path — the honest cost of materializing real `BaseModel` instances
  (still 1.59× fastapi at 12 workers, 14.2× at 1). Reject path is
  unaffected (validation never reaches the hook): 135,772, 98% of ceiling.
- **Reject ≠ validated for fastapi**: FastAPI's 422 path (79,431)
  outperforms its own plaintext (63,093) — the error envelope is fully
  async-resident. Any ≥20× criterion over FastAPI's reject throughput
  needs ≥1.59M req/s, ~11× this machine's transport bound: unreachable in
  principle on this stack.
- `bench-check` gates the four self apps at ±5%: `latest.json` re-baselined
  this pass; all rows +0.0% delta, `python_calls=0` verified on `reject`.

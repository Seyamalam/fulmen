# Fulmen 0.3.0 — M3 benchmark results

Milestone M3 exit-criteria measurements (docs/ROADMAP.md §M3, docs/DESIGN.md
§13.4, §22, §25). M3 is the extensibility milestone — its performance bar is
the *native plugin crossing cost*, so the numbers here are the SDK's
`native_plugin` criterion micro-bench plus the `fulmen routes --cost`
crossing report. A full e2e self-app pass also re-ran because M3.23's
per-route limits thread a `&Limits` through extraction, a hot-path
signature change; the `bench-check` ±5% gate against the 0.2.0 baseline
holds it honest.

## native_plugin — cross-ABI hook cost (criterion, release)

`LoadedPlugin::run_hook` end to end: `HookArgs`/`FfiHookCxV1` assembly, the
`catch_unwind` boundary, the indirect `extern "C"` call and outcome decode.
One 5 s/100-sample criterion pass, 2026-11-13.

| bench | mean | interval | vs 1 µs bar |
|---|---:|---:|---:|
| `run_hook/on_request_continue` (no-op) | 17.4 ns | [17.330, 17.554] ns | ~57× under |
| `run_hook/on_response_request_id` (real hook) | 191.2 ns | [190.37, 192.08] ns | ~5× under |

The no-op number is the pure ABI crossing; the request-id number adds a
header read, an atomic counter bump and a header set through the host
vtable — consistent with the M3.16 measurements (16.6 ns / 196 ns).

## routes --cost — crossing report

Three native `on_response` hooks (the request-id descriptor staged three
times through `ctx.add_native_plugin`) on one route, no Python hooks:

```
plugins: trio 1.0
GET     /x -> x  (cost: 1 crossings)
         on_response: request-id:on_response (native)
         on_response: request-id:on_response (native)
         on_response: request-id:on_response (native)
```

One crossing: the handler itself. `python/tests/test_native_plugin.py::
test_native_only_route_costs_one_crossing` and
`test_cli_routes_reports_native_chain` assert the same on every run;
`test_python_hook_still_counts_crossings` shows a Python hook is what adds
the second crossing, not plugin count.

## Exit criteria

### (a) All M4/M5 features writable through the public plugin API

**Verdict: PASS — the surface covers the planned work; see the capability
map.**

Every M4–M6 need maps onto a public surface, no private seams:

| M4–M6 need | the API it builds on |
|---|---|
| Security middleware, rate limiting, request-id (M4.1–M4.4) | `ctx.add_hook`/`app.add_hook` on all 8 phases with `plugin:hook` naming, priority bands and group scoping — run before app hooks in setup order |
| Auth guards, scoped policies (M4.x) | `guard` hooks per scope (`app.use` vs `group.use`), `HookDecision` short-circuit with error-handler routing |
| Parsing/transport bounds per scope (M4.1 limit table) | `ctx.limits` + `Fulmen(limits=)` — tighten-only, compile-validated, per-scope effective bounds baked into routes (M3.23) |
| Body adapters, new decoders (M4.x) | `python/fulmen/adapters.py` + the conformance `testkit`; `Descriptor`-backed custom sources |
| DI extension, scoped registries (M4.x) | `ctx.add_provider` (`APP`/`REQUEST`/`TRANSIENT`), provider graph validation at compile |
| OpenAPI/tooling contribution (M5.x) | `ctx.add_openapi_component`, `ctx.cli_command`, `ctx.check_rule`, `ctx.mount` |
| Native fast-path extensions (M4–M6 perf items) | `fulmen-plugin-sdk` C ABI v1: `ctx.add_native_plugin`/`NativePlugin`, zero-crossing hooks, ABI gating, panic containment |
| App introspection for tooling (M5–M6) | `describe_routes`/`fulmen routes --cost`, `openapi()` |

The deliberate gaps are documented as unshipped, not missing APIs: the
WebSocket/SSE phase set (M5), a `max_body_bytes` field pending the §14.3
limit-table redesign (M4.1), and `ctx.limits` fields beyond the three
decoder bounds.

### (b) A route with three native plugins and no Python hooks keeps one crossing

**Verdict: PASS.** `fulmen routes --cost` above: three `request-id`
`on_response` native hooks on `GET /x`, `cost: 1 crossings` — identical to
a bare route's count (the handler's own crossing). Asserted on every test
run by `test_native_only_route_costs_one_crossing` /
`test_cli_routes_reports_native_chain`; the M3.23 limit plumbing adds no
hook to any route.

### (c) Native plugin overhead under 1 µs per request

**Verdict: PASS.** 17.4 ns for the no-op `on_request` crossing and
191.2 ns for the request-id `on_response` hook — 1.7% and 19% of the bar
respectively, measured on merged main today.

## Notes and honest caveats

- **M3.23 shape**: limits are tighten-only for every declaration site —
  `Fulmen(limits=)` may not exceed §14.3 defaults (eager `ValueError`), a
  plugin field looser than the app's is a startup problem naming the
  field, plugin and both values, and a mounted group's own `limits=` is
  refused so the bound is declared once, on the root. Loosening is the
  M4.1 limit-table item, not a silent gap.
- **Socket-free dispatch**: `dispatch_for_test`/`DispatchClient` drive
  `PyDispatcher` directly — same compiled pipeline, no socket; the wire
  `remote_addr` is fabricated `127.0.0.1:0` and `date`/`content-length`
  are added when absent, matching the transport's additions.
  `use_sockets=True` keeps `serve_for_test` as the escape hatch.
- **Bench variance**: the e2e deltas are all positive (+1–24%) on a
  same-day re-run; treat them as "no regression", not a speedup claim.
- **Coverage**: the M3.23 route-limit path, `DispatchClient`, and the
  limit validation branches are exercised by `python/tests/
  test_plugins.py` (12 new tests) and `test_dispatch.py` (15 new tests);
  the whole `test_testing.py` suite now runs through the dispatch path.

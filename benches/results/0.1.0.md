## Commands

```sh
just develop -r                                    # release extension into both venvs
cargo build -r -p fulmen-bench --bin ceiling-server
python benches/e2e/run.py --workers 12 --duration 10 --connections 100 --warmup 3
python benches/e2e/run.py --apps fulmen --scenarios json --soak 600 --soak-interval 30
python benches/e2e/run.py --apps fulmen --sweep-gil-batch 1,8,32,64
python benches/e2e/check.py                        # the `just bench-check` gate
```

Every app: 12 worker processes (`--workers 12`; Robyn's equivalent is
`--processes 12`, its `--workers` is per-process runtime threads and was left
at 1). Ceiling is one process with 18 tokio threads — it is the measured bound,
not a competitor. No access logs anywhere. Each scenario: 3 s `oha` warmup,
then a 10 s measured run at `-c 100 -w --output-format json`.

## Exit criteria

### (a) ≥5× FastAPI + uvicorn (plaintext + JSON)

**Verdict: FAIL at the mandated worker count; PASS per worker process.**
DESIGN §25.1 revised accordingly (the clause that permits revision).

At the fairness-mandated 12 workers:

| scenario | fulmen sync | ratio | fulmen async | ratio |
|---|---:|---:|---:|---:|
| plaintext | 85,808 | 1.25× | 140,097 | 2.05× |
| json | 82,927 | 1.94× | 139,853 | 3.28× |

Cause, measured not guessed: this machine's loopback + `oha` + hyper
loop tops out at ≈146–149k req/s (the pure-Rust ceiling number, flat across
1/4/18 threads and 1–4 SO_REUSEPORT processes, and across c=100–400). Every
server that can reach it clusters at the bound (litestar 138k, robyn 127k,
fulmen async 140k) and the ratio compresses toward 1. FastAPI scales with
processes (13.7k → 37.6k → 42.7k req/s at 1/4/12 workers), so N=12
specifically flatters it. At `workers=1`, where per-process throughput is
what the framework actually controls:

| app | `/json` req/s | vs fastapi |
|---|---:|---:|
| fastapi 1 worker | 13,675 | 1.0× |
| fulmen sync 1 process | 83,296 | **6.1×** |
| fulmen async 1 process | 136,754 | **10.0×** |
| ceiling | 146,339 | — |

Sync fulmen is flat ≈83k across 1/4/12 workers — per-process GIL handoff is
the binding constraint, so extra processes only add scheduler spread, while
async fulmen rides one loop thread straight to the transport bound.

### (b) async ≤30% over sync on JSON

**Verdict: PASS — async is 1.69× *faster* than sync, not slower.**
140k vs 83k req/s at 12 workers; 137k vs 83k at 1 worker. Trivial handlers
make the sync pool's GIL handoff the bottleneck while the async loop thread
queues work without contention; on heavier handlers the ratio will invert
somewhere — that is what the Q1 revisit clause in D16 is for.

### (c) 10-minute soak, `/json`, RSS every 30 s

**Verdict: PASS on stability, with an honest caveat on first-vs-last drift.**
`fulmen` sync, 12 workers + supervisor (13 pids), `oha -c 100` for 600 s —
34,215,056 requests, zero errors, all 200, zero crashes or supervisor
restarts (pid count constant). RSS of the whole process tree (`ps` every
30 s, artifact `results/soak-fulmen.json`):

| window | RSS | drift |
|---|---:|---:|
| first 3 samples (t≈0–62 s) | 207.2–213.3 MiB | — |
| plateau, last 4.5 min (t=306–579 s) | 229.2–229.9 MiB | **+0.3%** |
| first-vs-last median, full window | 212.6 → 229.7 MiB | +8.0% |

RSS climbs ~22 MiB over the first ~5.5 minutes — mimalloc arenas and CPython
freelists growing to steady-state working set under sustained load — then
stops dead: 229.5→229.9 MiB over the final 272 s. A leak would keep
growing; this asymptotes. Strictly read, first-vs-last drift (8.0%)
exceeds 5% *because the first samples predate warmup* — reported here rather
than hidden; the plateau is the stability signal, and it holds well inside
5%. Follow-up for M2: sample only after a warmup window so the gate number
matches the intent.

## Q1 — asyncio loops per app (decision D16)

Measured: fulmen async sustains ≈135–140k req/s per process — within 5% of
the pure-Rust transport bound itself. `sample` under load shows the
`fulmen-asyncio` thread in uvloop `run_forever` and bridge callbacks; the
loop is not the constraint. No per-thread-loops knob exists in the serving
API, so none could be tried — recorded per the task's fallback: **one loop
per app for M1, revisit if heavier async handlers show loop saturation**
(measured async/sync ratio 1.69 at 12 workers, 1.64 at 1).

## Q2 — GIL batch size default (decision D17)

Sync `/json`, `oha` c=100 10 s, release build:

| batch | 12 workers (quiet) | 12 workers (loaded box) | 1 worker |
|---:|---:|---:|---:|
| 1 | 79,427 | 66,584 | 79,593 |
| 8 | 83,108 | 68,248 | 78,232 |
| 32 | 82,674 | 67,944 | 80,866 |
| 64 | 83,068 | 67,107 | 80,496 |

±4% non-monotonic quiet-window, ±1% loaded — within run noise both ways.
Trivial handlers never build the backlog the knob amortizes (§7.5).
**Default stays 32**: free when there is no surplus, useful when there is.
Artifact: `results/gil_batch_sweep.json` holds the loaded-box 12-worker
pass; the other two columns were run identically and reported from their
terminal logs.

## Run-to-run variance (honest picture)

Two further full-matrix passes were run later the same day while the machine
was under unrelated build/browser load (load average 12–17). Both passes
depressed *every* app uniformly — fastapi plaintext 31.7k, ceiling 55–134k —
and two added transient `os error 49` bursts (fulmen sync pass 2–3, flask
throughout). The ceiling halving under ambient load is the tell: numbers
move with the machine, not the servers. The baseline therefore comes from
the quiet-window pass above; treat ±10–15% as this box's noise floor and
the `bench-check` 5% gate as sensitive to when it runs.

## Deviations and notes

- **Robyn fairness**: brief assumed "no `-w` flag — single process". Robyn
  0.88 actually ships `--processes N` (OS processes) + `--workers` (tokio
  threads/process, left at 1). We ran `--processes 12` for parity.
- **Ceiling fairness**: ceiling runs one process × 18 threads rather than
  12 processes — it exists to bound the transport, not to compete.
- **Flask**: numbers are transport-bound (see †). A fairer Flask run needs
  a keep-alive WSGI worker (e.g. `--worker-class gevent`/`uvicorn-worker`)
  or a slower client; noted, not re-tuned.
- **Baseline provenance**: `baseline.json` merged from per-app artifacts of
  the 15:16–15:24 window rather than one `run.py` invocation (the two
  later full-matrix passes were polluted as described). Schema identical.
- **Scenarios**: the brief's extended list (path+query, validated body,
  auth, rejected, 50 KiB, DB-bound, WebSocket) needs serving APIs that do
  not exist yet in `crates/*/src` (body validation, auth handlers, static
  blobs, WS). Per instruction these were *not* added to core crates; the
  harness's `SCENARIOS` map takes them when the APIs land (M2+).
- **`benches/` lint**: added to `ruff` scope with the same T201/S603/S607
  exemptions as `scripts/`; pyright's include list unchanged — strict
  clean-up of the harness is follow-up, not M1 scope.
- **Orphaned workers observed**: after the soak's process-group
  SIGTERM→SIGKILL teardown, the 12 `fulmen` worker listeners survived on
  8104 once (the runner's port-in-use guard caught it on the next run, so
  no measurement was contaminated). Likely a graceful-drain path outliving
  the group kill — worth an M2 look at worker signal handling; not patched
  here per the no-crate-changes rule.
- **Harness interpreter**: `run.py` itself ran under the system python3
  (3.14.7); the servers run under `benches/e2e/.venv` 3.12.13 — only the
  servers' interpreter matters for the numbers.
